# 照片管理器：在已安装插件详情页里设置照片

> 状态：已定稿，交给实现拆票（本地 issue tracker：`.scratch/photo-manager/`，实现票在 `issues/`）。
> 相关：ADR `docs/adr/0001-photos-live-in-dsh-home.md`、术语表 `GLOSSARY.md`。

## Problem Statement

用户想给输入框下方的晾衣绳换几张自己的照片，但现在这件事被做成了文件系统运维：得打开 Finder，把图片拷进插件的 `photos/` 目录（npm 安装时还是 `node_modules` 里的包目录），再回聊天页等 5 秒确认有没有生效；想删一张、换一张、调顺序，只能继续翻文件、改文件名。更糟的是这个目录属于安装产物：装一次更新，照片就没了，而用户直到发现绳子变回内置插画才知道。

## Solution

照片改在**已安装插件的详情页**里管理：插件详情页出现「照片」区，列出全部照片，多选添加、删除、拖动排序；**顺序里的前 6 张上绳**，绳子和列表在写完后立刻刷新。照片存放在用户数据目录（`$DSH_HOME/dsh-snap-line/photos`），升级插件不会丢；原图与显示版分离——晾衣绳和列表加载几百 KB 的显示版，灯箱加载原图。手工把文件放进照片目录的老用法保留。1.3.x 放在插件包里的旧照片不迁移，用户在详情页重新添加。

## User Stories

1. 作为安装了 SnapLine 的 Harness 用户，我想在插件详情页看到当前所有照片，以便知道绳上会挂哪几张。
2. 作为用户，我想在详情页多选文件一次性添加，以便不用再开 Finder 复制。
3. 作为用户，我想把图片直接拖进详情页的照片区完成添加，以便比文件对话框更快。
4. 作为用户，我想在添加后立刻看到绳子和列表更新，以便不用刷新页面或重启 Harness。
5. 作为用户，我想删除某张照片并让原图、显示版、顺序记录一起清掉，以便不留垃圾。
6. 作为用户，我想在删除前被二次确认，以便不会误删私人照片。
7. 作为用户，我想拖动照片调整顺序，以便决定哪 6 张上绳以及它们在绳上的先后。
8. 作为只用键盘的用户，我想用上移/下移按钮调整顺序，以便不依赖拖动。
9. 作为用户，我想在列表里看到「在绳上」标记和前 6 张的边界，以便理解排序和上绳的关系。
10. 作为用户，我想点开缩略图查看原图，以便确认细节而不被显示版限制。
11. 作为用户，我想在选错文件（超大、格式不支持、HEIC）时看到就地错误说明，以便知道该怎么处理。
12. 作为用户，我想重复添加同名文件时得到新名字而不是覆盖旧照片，以便不会意外丢失已有照片。
13. 作为用户，我想升级插件后照片仍然在，以便不用每次更新都重新添加。
14. 作为用户，我想卸载插件后照片目录仍然保留，以便之后重装还能继续用。
15. 作为用户，我想仍然可以直接把图片拷进照片目录，并在 5 秒内看到它上绳，以便保留脚本化的老用法。
16. 作为用户，我想打开详情页时让手工放入的照片自动补上显示版，以便绳子不会因为原图太大而变慢。
17. 作为用户，我想清空照片目录后回到内置插画，以便有一个干净的兜底状态。
18. 作为用户，我想确认照片不会离开本机、不会被上传，以便放心放私人照片。
19. 作为用户，我想从 1.3.x 升级后知道旧照片为什么不见了、要怎么重新添加，以便这不是一个静默故障。
20. 作为使用键盘/读屏器的用户，我想照片管理器可以被 Tab 聚焦、按钮有可读名称，以便它和晾衣绳本身一样可用。
21. 作为插件作者，我想让照片数据完全由插件自己维护在用户目录里，以便 npm 包里永远不出现私人照片。
22. 作为插件作者，我想让写入端只接受图片、限制单张大小并校验来源，以便陌生人无法从网页往照片目录里写文件。
23. 作为插件作者，我想让清单接口同时给出原图和显示版的地址，以便 Client 半不用知道存储细节。
24. 作为插件作者，我想让「哪 6 张上绳」的规则由 Host 半计算并写进清单，以便 Client 半只渲染、规则只需测一处。
25. 作为用户，我想在详情页里看到照片数量与上绳数量的摘要，以便一眼判断是不是加多了。

## Implementation Decisions

**模块**

- Host 半入口：在现有读路由之外注册一条写路由，并把照片目录从"插件包内"改成用户数据目录；解析规则与官方 `dsh-home-paths` 一致（`DSH_HOME` 优先、否则 `~/.dsh`）。
- 照片目录库：从"只读清单/读文件"扩展为照片目录的完整读写面——清单、原图、显示版、顺序、校验、原子写入。保持纯 Node、无 Cordis、无 DOM，便于单测。
- Client 半：新增照片管理器界面（注册在插件管理页的 `plugins.bundle.config` 插槽，按包名 keyed），以及添加照片时的显示版生成；晾衣绳继续消费清单。
- 本地化：管理器文案走 `ctx.locale.register`，中英双份，与现有读屏名称风格一致。
- 文档：README 中英、CHANGELOG、`photos/README.md`、ADR、GLOSSARY。

**照片目录**

- 位置：`$DSH_HOME/dsh-snap-line/photos`（默认 `~/.dsh/dsh-snap-line/photos`）。不再读取插件包内的 `photos/`。
- 布局：原图平铺在目录根；显示版在 `.display/<name 的哈希>.jpg`；顺序在 `.order.json`。隐藏项（`.` 开头）永不进入清单，也不可被读取路由访问。
- 写入：先写临时文件再 rename；同名文件不覆盖，自动追加 `-2`、`-3` 之类后缀；名字取 basename、去掉路径分隔符与隐藏前缀、限制长度。
- 删除：同时删除原图、对应显示版和顺序条目。

**清单接口**（`GET /dsh-snap-line/photos.json`）

- 保留 `revision`（mtime 哈希）用于缓存失效。
- `photos` 数组按顺序返回全部照片，每项含：名字、显示版地址（缺失时回退原图地址）、原图地址、是否在绳上。
- 顺序规则：`.order.json` 里列出的文件按序在前，未列出的按文件名自然排序追加；前 `MAX_PHOTOS` 张标记为在绳上。读路由仍是只处理 GET/HEAD 的 resource。

**写路由**（`POST /dsh-snap-line/manage`）

- 单一路由、四个动作，动作由 path/query 或 JSON 字段区分：添加（请求体是图片原始字节，文件名在 query）、删除（JSON：名字）、排序（JSON：完整名字数组）、写显示版（请求体是显示版字节，文件名在 query）。
- 响应为 JSON；成功 200，参数错误 400，不支持的媒体类型 415，超限 413，来源不被信任 403。
- 来源策略（插件路由本身没有 DSH 鉴权，必须自己守）：写请求必须同源——`Origin` 与 webServer 的 origin 一致，且拒绝 `Sec-Fetch-Site: cross-site`。
- 校验：扩展名与 `Content-Type` 都在允许集合内，并用 magic bytes 复核；单张 ≤ 25MB、像素 ≤ 64MP；HEIC 直接拒绝并返回可读原因。
- 实现为 webServer 的 `handler` 路由（resource 只接受 GET/HEAD），内部把 Node 请求适配成 Fetch 风格的 `Request` 再交给可单测的写入函数。

**显示版**

- 在浏览器里用 canvas 从原图生成：长边 1280、JPEG 质量约 0.82；原图按原字节保存。
- 动图（GIF / AVIF）的显示版取首帧，原图保留动画。
- 清单缺显示版时回退到原图；照片管理器打开时为缺少显示版的照片补生成（幂等）。
- 灯箱始终加载原图；晾衣绳、列表缩略图加载显示版。

**Client 行为**

- 管理器在插件详情页里渲染，只有 `subject.kind === 'bundle'` 且包名为本插件时才出现。
- 添加：文件选择（多选）+ 拖放；删除：确认后再调用；排序：拖动 + 上移/下移按钮。
- 写完照片后派发一个窗口事件，晾衣绳与管理器立即重取清单；5 秒轮询保留作为兜底。
- 空照片目录时管理器显示与"内置插画"一致的空状态说明。

**迁移与兼容**

- 不迁移旧照片：包内 `photos/` 不再读取；README 与 CHANGELOG 写明"从 1.3.x 升级需在详情页重新添加"。
- 卸载插件不删除照片目录。
- 不新增运行时依赖，保持零构建、零 ESM 依赖，`engines.dsh` 不变。

## Testing Decisions

**什么叫好测试**：只测外部可观察行为——给一个照片目录和一个 HTTP 请求，断言状态码、响应体、响应头和目录里的结果文件；不 mock 内部函数，不测像素级界面。

**缝（seam）**：沿用现有最高缝——Host 半的 HTTP 面（Fetch 风格的 `Request` → `Response`）。

- 读侧继续由现有清单/图片 resource 承担，测试直接调用它。
- 写侧新增一个同形状的写 resource（`Request` → `Response`），由 webServer 的 `handler` 适配器包一层；测试直接调写 resource，不测 Node 适配器（只保留一条"两条路由都已注册"的入口测试）。
- 只有一处新缝：写 resource。Client 界面与 canvas 显示版生成不引入自动化测试（仓库没有 DOM 测试环境，也不打算为它加依赖），靠手工验收。

**测哪些**：

- 照片目录库：清单顺序（列出/未列出/自然排序）、上绳标记、显示版回退、revision 变化、读取路由的 404/400 边界（沿用现有用例）。
- 写 resource：添加成功（原图落盘、清单可见「在绳上」）、同名不覆盖、超限 413、不支持类型 415、magic bytes 不符 400、路径穿越/隐藏名被拒、删除同时清理原图与显示版与顺序条目、删除不存在的名字、排序写入与读取一致、写显示版后可被清单引用、跨站来源被拒 403。
- Host 半入口：注册了读 resource 与写 handler 两条路由（路径、kind、resource/handler 类型）。
- 仓库清单测试：包内不再出现照片目录、新增的 ADR/GLOSSARY 与 README 关键链接仍在。

**先例**：`test/photos.test.js` 用临时目录 + magic-byte 夹具 + Fetch `Request`/`Response` 断言；`test/manifest.test.js` 对包与仓库文件做不变量检查。

## Out of Scope

- 旧照片自动迁移/导入（1.3.x 的照片不迁移，重新添加）。
- 照片编辑：裁剪、旋转、重命名、说明文字、滤镜。
- 每个 profile 独立的照片目录（ADR 0001 决定全局一份）。
- 照片数量上限、显示版尺寸、上绳数量的界面配置（仍是代码常量）。
- 云同步、分享、任何外部网络请求。
- 修改内置插画或晾衣绳视觉本身。
- Client 界面的自动化测试（无 DOM 测试环境）。
- 插件市场截图更新（实现完成后手工替换）。
- 通用"插件设置"能力或修改 DSH 本身。

## Further Notes

- 当前注册的安装方式是 `link:` 到仓库，所以作者现有的 6 张照片在仓库 `photos/`（未跟踪）；按 Q6=D 的决定它们不会迁移，需在详情页重新添加，旧文件可自行保留或删除。
- DSH 插件路由没有鉴权、`resource` 只接受 GET/HEAD、没有 multipart 解析器、没有插件数据目录服务——这四点决定了上面的接口形状。
- 本仓库的 tracker 是 `.scratch/` 下的本地 markdown（见 `docs/agents/issue-tracker.md`）；spec 定稿后按依赖顺序拆成 `issues/NN-*.md`。
